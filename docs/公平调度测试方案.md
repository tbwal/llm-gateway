# 公平调度（Fair Scheduler）测试方案

> 覆盖 `internal/scheduler/fair.go` 的账本式公平调度、渠道×模型冷却，
> 以及与 `relay.go pickChannel` 的集成。测试分四层：单元 → 集成 → 端到端 → 异常。

## 一、L1 单元测试（`internal/scheduler/fair_test.go`，已落地）

| 测试 | 验证什么 | 断言 |
|---|---|---|
| `TestFairUniform` | 均匀性 | 5 渠道 weight=1，选 10000 次，每渠道 ∈ [1900, 2100]（±5%） |
| `TestFairWeighted` | 权重比例 | weight 1:2:1，选 12000 次，比例 ≈ 1:2:1（±5%） |
| `TestShortWindowNoJitter` | 短窗口防抖 | 同权重 5 渠道连选 20 次，单渠道 ≤ 6 次（加权随机会出现 8+） |
| `TestCooldown` | 冷却粒度 | 失败只摘 (渠道, gpt-5)，(渠道, deepseek-chat) 照常；10s 过期后恢复 |
| `TestConcurrent` | 并发安全 | 8 协程 × 500 次，无数据竞争 |
| `TestSelectEmpty` | 边界 | 空候选 / 唯一候选在冷却中 → 返回 false |

建议补充：
- `TestAdmissionCalibration`：新渠道加入后首轮不被选（入场校准 Progress=watermark 生效）
- `TestAntiMonopoly`：极端权重 1:100，防霸屏（Consecutive≥8 强制让位）触发

运行：`go test -count=1 ./internal/scheduler/ -v`

## 二、L2 集成测试（真实链路，`internal/handler/relay_scheduler_test.go`）

与 L1 的区别：走真实 `pickChannel`（过滤器 + 公平调度 + 真实落库），验证跨请求账本保持。

```
TestFairSchedulerEndToEnd
 ├─ 建 3 渠道：mock-a(weight=1) / mock-b(weight=2) / mock-c(weight=1)
 │    models 同模型，base_url 指向同一 httptest mock 上游
 ├─ 建 1 key：scopes 覆盖测试模型
 ├─ NewRelayHandler（内部创建 FairScheduler，跨请求共享账本）
 ├─ 发 60 个请求（同一 handler 实例）
 └─ 查 usage_logs 按 channel_id 统计
     断言① 每个渠道都 > 0（无饿死）
     断言② 比例 ≈ 1:2:1（±8%）
     断言③ 总量 = 60（全成功）

TestFairSchedulerFailover
 ├─ 渠道 A 指向返回 500 的假上游，B/C 指向好上游
 ├─ 发 30 个请求
 └─ 断言：A 被熔断+冷却摘除，后续全走 B/C，usage_logs 中 A 无后续成功记录
```

核心断言逻辑（为什么能断言精确比例）：
**公平调度是确定性的（无随机）**——60 次后比例几乎精确等于 1:2:1。
这是与加权随机的本质区别：随机只能断言统计区间，公平调度可以断言精确值。

## 三、L3 端到端测试（真实服务 + 真实压测，本次已执行）

### 环境

- 网关 :8080（新代码）+ mock 上游 :9090（`cmd/mockupstream`）
- 渠道：`deepseek-v1-flash` 有 2 个 → id=4 DeepSeek(weight=2) + id=7 dsh(weight=1)
- key：scopes 必须含 `deepseek-v1-flash`

### 步骤

```
① 确认服务在跑：netstat -ano | findstr :8080 :9090
② 确认是新代码：发 1 个请求，请求日志出现 "[pick] 公平调度选中"
③ 压测 200 个请求（8 协程 × 25，PS 5.1 用 Start-Job 不用 -Parallel）
④ 统计 usage_logs 按渠道分布
```

压测脚本（PowerShell 5.1 兼容）：

```powershell
$key='sk_lgw_你的key'
1..8 | % { Start-Job -ScriptBlock { param($k)
    $h=@{Authorization="Bearer $k";'Content-Type'='application/json'}
    $body='{"model":"deepseek-v1-flash","messages":[{"role":"user","content":"hi"}],"stream":false}'
    for($i=0;$i -lt 25;$i++){ try{ Invoke-WebRequest -Uri 'http://localhost:8080/v1/chat/completions' -Method Post -Headers $h -Body $body -UseBasicParsing|Out-Null }catch{} }
} -ArgumentList $key } | Wait-Job | Remove-Job
```

统计（写 .py 文件执行，避免 PowerShell 引号地狱）：

```python
import sqlite3
db = sqlite3.connect(r'E:\front\后端\llm-gateway\data\llm-gateway.db')
for r in db.execute(
    "SELECT channel_id, channel_name, COUNT(*) FROM usage_logs "
    "WHERE model='deepseek-v1-flash' AND created_at > datetime('now','-1 hour') "
    "GROUP BY channel_id ORDER BY channel_id"):
    print(r)
```

### 判定标准

```
比例 ≈ weight 比例（2:1）±5%    ← 确定性收敛
且每个渠道都 > 0                 ← 无饿死
```

## 四、L4 异常场景（手工验证）

| 场景 | 操作 | 预期 |
|---|---|---|
| 单渠道故障 | 把渠道 A 的 base_url 指向死端口（如 :9999）→ 压测 | A 熔断+冷却摘除，流量全分流健康渠道，日志出现「熔断冷却中/模型冷却，跳过」 |
| 冷却自动恢复 | 等冷却期（熔断 30s / 模型冷却 10s）后再压 | A 重新入候选池 |
| 全渠道失败 | 所有渠道指向死端口 | 502「所有渠道均不可用」 |
| 权重热更新 | 压测中改 weight | 比例平滑切换到新权重（channelCache 无锁快照热更新） |

## 五、本次实测数据（2026-10-29，真实环境）

### ① 权重比例（200 请求压测）

```
渠道 4 DeepSeek (weight=2): 136 次   ← 期望 ~133
渠道 7 dsh      (weight=1):  69 次   ← 期望 ~67
比例 = 136 : 69 ≈ 1.97 : 1 ≈ 2:1 ✅   误差 < 1.5%
```

### ② 账本记忆（15:37 请求日志）

压测后 id=4 累计被选 ~140 次（share=140/2=70），id=7 累计 69 次（share=69/1=69），
**share 更小的 id=7 被选中**——即使它 weight=1：

```
[pick] 公平调度选中渠道 id=7 dsh（weight=1，共 2 候选）
```

### ③ tick 规则（15:42 请求日志）

id=7 刚被选过（LastSelected 新），share 并列时补更久没被选的：

```
[pick]   渠道 id=7 dsh：入候选池（weight=1）        ← 冷却过期，自动恢复
[pick] 公平调度选中渠道 id=4 DeepSeek（weight=2，共 2 候选）
```

### ④ 冷却跳过（15:44 请求日志）

id=7 base_url 指向死端口 → 连续失败 → 熔断 OPEN → 跨请求摘除：

```
[pick]   渠道 id=7 dsh：熔断冷却中，跳过            ← 跨请求冷却生效
[pick] 最终候选 1 个
[pick] 公平调度选中渠道 id=4 DeepSeek（weight=2，共 1 候选）
```
